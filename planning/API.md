# Busreisen SaaS — REST API Design v1.0

Companion to PRD MVP v1.1. Backend: FastAPI. Database: PostgreSQL, schema-per-tenant. Payments: Stripe.

---

# 1. Overview

One API, one version (`/v1`), three audiences:

| Surface | Audience | Auth | Tenant resolved from |
| --- | --- | --- | --- |
| **Platform** (`/v1/platform/*`) | Prospective operators (signup) | none / Stripe | none (writes to `public` schema) |
| **Shop** (`/v1/shops/{shop_slug}/*`) | Passengers (no login) | none (booking access token for own booking) | `shop_slug` in the path |
| **Tenant** (everything else) | Admin, Staff, Driver | JWT | `tid` claim in the token |

Design rules that follow from this:

- On authenticated routes the tenant **never** comes from the URL, a header or the body. Only the JWT claim counts.
- On shop routes the tenant comes only from `shop_slug`. The Astro SSR server maps host → slug via `GET /v1/shops?host=…` (cache it).
- The API resolves the tenant, validates it against `public.tenants`, then runs `SET LOCAL search_path TO tenant_<id>, public` inside the request transaction. Schema names come only from the `tenants` table.

# 2. Conventions

| Topic | Rule |
| --- | --- |
| Base URL | `https://api.<platform-domain>/v1` |
| Format | JSON (`application/json`), UTF-8. Errors: `application/problem+json` (RFC 9457) |
| Naming | Plural nouns for collections, `kebab-case` in paths, `snake_case` in JSON fields |
| IDs | UUIDv7 as strings. Bookings additionally carry a human-readable `ticket_number` (e.g. `BR-7K4M2Q`, unique per tenant) |
| Timestamps | ISO 8601 UTC with `Z` (`2026-11-03T06:30:00Z`). Departure times additionally carry the IANA `timezone` of the travel |
| Money | Integer minor units + currency: `{"amount_cents": 4500, "currency": "EUR"}`. No floats |
| Methods | `GET` read, `POST` create / non-CRUD action, `PUT` full replace, `PATCH` partial update (JSON Merge Patch, `application/merge-patch+json`; arrays are replaced as a whole), `DELETE` remove |
| Status codes | `200` OK, `201` Created (+ `Location`), `202` Accepted (async), `204` No Content, `400` malformed, `401`, `403`, `404`, `409` state/capacity conflict, `412` ETag mismatch, `415`, `422` validation, `428` missing `If-Match`, `429` |
| Single resources | Returned bare: `{ "id": "...", ... }` |
| Collections | `{ "data": [...], "page": { "next_cursor": "…", "has_more": true } }` plus `Link: <…>; rel="next"` |
| Pagination | Cursor-based: `?limit=25&cursor=…`. Default 25, max 100 |
| Sorting | `?sort=departure_at,-created_at` (`-` = descending). Each collection lists its allowed fields |
| Filtering | Plain query params per field (`?status=published&departure_from=…&departure_to=…`), free text via `?q=` |
| Expansion | `?expand=travel` on bookings; sparse fields are not supported in v1 |
| Concurrency | Every mutable resource returns an `ETag`. `PATCH`/`PUT`/`DELETE` on staff-edited resources (travels, bookings, users) require `If-Match`, otherwise `428`; mismatch gives `412` |
| Idempotency | `Idempotency-Key` header is **required** on `POST /shops/{slug}/bookings`, `POST /bookings`, `POST /platform/signups` and accepted on every other `POST`. Stored 24 h. Same key + same body returns the original response, same key + different body returns `422` |
| Versioning | Major version in the path. Additive changes (new fields, endpoints, enum values) are non-breaking, so clients must ignore unknown fields. Deprecations announced via `Deprecation` and `Sunset` headers |
| State transitions | Modelled as `POST` to an action sub-resource (`/travels/{id}/publish`), because a status `PATCH` would hide the guard rules. This is the only place verbs appear in paths |
| Content negotiation | `Accept: text/csv` or `application/pdf` on export endpoints; `?format=csv` as fallback for plain links |
| Rate limits | `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`; `429` with `Retry-After` |
| Request tracing | Every response carries `X-Request-Id`; it is also echoed in error bodies |
| Docs | OpenAPI 3.1 at `/v1/openapi.json` (generated by FastAPI); Swagger UI only in non-production |

# 3. Authentication & authorization

## 3.1 Tokens

- **Access token:** JWT, 15 min, `Authorization: Bearer …`. Claims: `sub` (user id), `tid` (tenant id), `role` (`admin` | `staff` | `driver`), `exp`.
- **Refresh token:** opaque, 30 days, rotated on every use, stored hashed. Web clients get it as `HttpOnly; Secure; SameSite=Strict` cookie scoped to `/v1/auth`. Reuse of an old refresh token revokes the whole token family.
- Login is by email + password (Argon2id). Login identifies the tenant by email plus the tenant's admin/driver domain; a user belongs to exactly one tenant in v1.
- Shop endpoints are anonymous. A passenger accesses **their own** booking via a signed `access_token` (random, 32 bytes, stored hashed, delivered in the confirmation email link and in the booking-creation response).

## 3.2 Role matrix

`A` = Admin, `S` = Staff, `D` = Driver, `—` = no access. Anonymous shop access is listed separately in section 4.

| Resource | A | S | D |
| --- | --- | --- | --- |
| Tenant settings, domain, branding | RW | R | — |
| Subscription / billing / payment account | RW | — | — |
| Users | RW | — | — |
| Travels | RW | RW | R (assigned only) |
| Bookings | RW | RW | — |
| Passengers | RW | RW | R (assigned travels), PATCH `boarded` only |
| Dashboard | R | R | — |
| Exports (CSV/PDF) | R | R | — |
| Tenant data export / anonymization | RW | — | — |

Drivers are filtered server-side to travels where `driver_id = sub`; they receive `404` (not `403`) for anything else to avoid leaking existence.

# 6. Booking, reservation and payment flow

The PRD's "reserve places for ~15 min" is implemented as a **booking in status `pending_payment`**. No separate reservation resource is needed, and a single `POST` is atomic.

## 6.1 Shop booking sequence

1. `POST /shops/{slug}/bookings` runs in one transaction:
   1. Validate travel is `published`, in the future, prices belong to the travel.
   2. Reserve places with an atomic conditional update on the travel row:
      `UPDATE travels SET reserved = reserved + :n WHERE id = :id AND capacity - booked - reserved >= :n`.
      Zero rows updated → `409 insufficient_capacity`.
   3. Insert booking (`pending_payment`, `expires_at = now + 15 min`) and passengers.
   4. Create the Stripe Checkout session on the operator's connected account, with `client_reference_id = booking_id`, metadata `{tenant_id, booking_id}` and the same `Idempotency-Key` towards Stripe.
   5. If Stripe fails, roll back (places are released) and return `502 payment_provider_error`.
2. Client redirects the passenger to `checkout_url`.
3. Stripe webhook `checkout.session.completed` → booking `confirmed`, `reserved -= n`, `booked += n`, ticket email sent (outbox pattern, see 6.3).
4. The passenger returns to the shop, which polls `GET /shops/{slug}/bookings/{id}?token=…` until `status = confirmed` (webhook may arrive after the redirect).

## 6.2 Expiry

- A background job (every minute) finds `pending_payment` bookings with `expires_at < now`, sets them to `expired`, decrements `reserved`, and calls Stripe `checkout.sessions.expire` on the session.
- Stripe requires Checkout sessions to live at least 30 minutes when `expires_at` is set at creation, so the API does **not** rely on Stripe's own expiry. It expires the session explicitly.
- Edge case, payment completes right as the reservation expires: the webhook handler tries to re-reserve. If places are still available the booking is confirmed. If not, the payment is refunded automatically and the booking stays `expired` (`payment.status = refunded`), and the passenger is emailed.
- `checkout.session.expired` webhook is treated as a second trigger for the same release logic (idempotent).

## 6.3 Consistency rules

- `booked`, `reserved` counters are updated only in the transactions above. A nightly job recomputes them from bookings and alerts on drift (target: zero overbooking incidents).
- Emails are written to an `outbox` table in the same transaction as the state change and sent by a worker, so a crash never loses or duplicates a confirmation.
- Staff manual bookings use the same capacity update but skip `pending_payment`.
- Cancelling a `confirmed` booking: `booked -= n`. Cancelling `pending_payment`: `reserved -= n` and Stripe session expired.

# 7. Webhooks (Stripe → API)

Single endpoint `POST /v1/webhooks/stripe`.

- Verify the `Stripe-Signature` header with the endpoint secret against the raw body. Reject with `400` otherwise.
- Store `event.id` in `public.processed_events` first. Already seen → return `200` without processing (Stripe retries).
- Answer `2xx` fast; heavy work goes to a queue.
- Route by event:

| Event | Source | Action |
| --- | --- | --- |
| `checkout.session.completed` (mode `subscription`) | platform account | Start tenant provisioning |
| `customer.subscription.updated` / `deleted` | platform account | Update `subscription.status`; `past_due` → grace period banner, `canceled` → shop read-only |
| `invoice.payment_failed` | platform account | Notify admin, mark `past_due` |
| `checkout.session.completed` (mode `payment`) | connected account | Confirm booking (section 6) |
| `checkout.session.expired` | connected account | Release reservation |
| `charge.refunded` | connected account | Set `payment.status = refunded` (refunds are made in the Stripe dashboard in MVP) |
| `account.updated` | connected account | Update `payment-account.status` |

- Connected-account events carry `account`; the handler resolves it to a tenant via `public.tenants.stripe_account_id`, then sets `search_path` like any other request.

# 8. Errors

| Status | `code` | When |
| --- | --- | --- |
| 400 | `malformed_request` | Invalid JSON, wrong content type parameters |
| 401 | `unauthenticated` / `token_expired` | Missing/invalid/expired token |
| 403 | `forbidden` | Role lacks permission, subscription `canceled` for writes |
| 404 | `not_found` | Unknown resource, or not visible to the caller (drivers, cross-tenant) |
| 409 | `insufficient_capacity` | Not enough places |
| 409 | `invalid_state` | Transition not allowed (e.g. publish a cancelled travel, cancel travel with active bookings) |
| 409 | `payment_account_not_ready` | Shop booking before Stripe Connect is active |
| 409 | `conflict` | Uniqueness (slug, email, domain) |
| 412 | `precondition_failed` | `If-Match` does not match current ETag |
| 415 | `unsupported_media_type` | Wrong `Content-Type` |
| 422 | `validation_error` | Field errors in `errors[]`; idempotency key reused with different body |
| 428 | `precondition_required` | `If-Match` missing on guarded write |
| 429 | `rate_limited` | Too many requests, see `Retry-After` |
| 502 | `payment_provider_error` | Stripe call failed |
| 503 | `service_unavailable` | Dependency down, retry |

Never leak stack traces or SQL. Cross-tenant access attempts return `404` and are logged.

# 9. Cross-cutting concerns

## Security

- HTTPS only, HSTS. CORS allow-list built from `tenants.domains` (shop hosts) plus the admin/driver app origin; no wildcard with credentials.
- Rate limits (per IP unless authenticated): public read 120/min, `POST /shops/*/bookings` 10/min, `POST /auth/tokens` 10/min per IP and per email, everything authenticated 600/min per user.
- Optional bot protection on `POST /shops/*/bookings` via Turnstile/hCaptcha token in `X-Captcha-Token`; switch on if abuse of reservations (hoarding places) shows up.
- Input limits: max body 1 MB (logo upload 1 MB dedicated), max `places` per booking 20, string length limits in schema.
- Passwords: Argon2id, breach-list check on set. Secrets in Azure Key Vault.
- Audit log (append-only) for user management, booking cancellation/edits, anonymization, domain and payment-account changes.

## GDPR

- Minimal PII: name, email, phone (optional) per booking; no birth dates or addresses.
- `POST /bookings/{id}/anonymization` and a retention job (default: anonymize passenger data 12 months after departure, configurable per tenant).
- `POST /tenant/exports` produces a schema-only dump plus CSVs (see PRD: `pg_dump --schema`).
- Access tokens and refresh tokens are stored hashed. Logs must not contain request bodies of bookings or auth endpoints.

## Caching & performance

- Public GETs: `ETag` + short `max-age`, CDN in front of the shop API.
- Staff GETs: `ETag` + `Cache-Control: private, no-cache`.
- Driver manifest: `ETag` and `updated_since` delta so the app can cache offline and sync cheaply.
- Indexes to plan for: `travels(status, departure_at)`, `bookings(travel_id, status)`, `bookings(ticket_number)`, `passengers(booking_id)`, unique `bookings(idempotency_key)` in `public.idempotency_keys(tenant_id, key)`.
- Target (PRD): p95 < 150 ms for reads; booking flow under 3 s (dominated by the Stripe session call).

## Observability

- Structured JSON logs with `request_id`, `tenant_id`, `user_id`, route, status, latency.
- Metrics: booking creations, `insufficient_capacity` rate, expired reservations, webhook failures, counter drift, provisioning failures.
- Alerts: any counter drift, webhook error rate > 1 %, provisioning `failed`.

# 11. Assumptions and open questions

1. **Stripe Connect is required.** Passengers pay the operator, not the platform, while the PRD only names Stripe Billing (operator subscription) and Checkout. This design assumes **Connect with Standard accounts and direct charges**: money goes straight to the operator, the operator handles Stripe fees and refunds, the platform takes no cut in MVP. If you want to take a booking fee or handle payouts, switch to Express accounts with destination charges; the endpoints stay the same, the webhook and onboarding details change. Please confirm.
2. **Users belong to exactly one tenant.** Same email in two tenants is not supported in v1.
3. **Refunds are out of scope** (PRD), so cancelling a paid booking does not move money. The admin refunds in the Stripe dashboard, and `charge.refunded` updates the booking.
4. **Currency is EUR** only in v1; the field exists for later.
5. **Ticket delivery** is an email with ticket number and a link (no PDF ticket / QR code in MVP). A QR code for boarding scan can be added later as `GET /bookings/{id}/ticket`.
6. **Tax handling** (VAT on tickets, invoices) is not covered by the PRD and is not part of this API.
